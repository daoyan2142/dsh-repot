# dsh-repot

**把 DSH 环境从一台机器搬到另一台。**

名字取「换盆」：连根带土原样挪到新盆，根不能动。插件、配置、文件夹经一个私有 GitHub / Gitee 仓库中转；还原时路径必须落在预期位置，否则拒绝写入。

## 它搬什么

| 类别 | 搬 | 怎么搬 |
|---|---|---|
| 插件（registry 安装） | ✅ | 默认只记 `名字@版本`，还原时重装；可选携带 tarball |
| 插件（`file:` 链接的源码） | ✅ | 源码目录整个搬过去，还原时重写成相对路径 |
| 插件（`file:` 指向的 tgz） | ✅ | 原样搬 |
| 配置 | ✅ | `cordis.patch.yml` / `package.json` / `pnpm-lock.yaml` / `pnpm-workspace.yaml` |
| 文件夹 | ✅ | 选定目录的快照，带路径锚 |
| 任务 / 会话 | ❌ | 会话是 zstd 压缩的追加日志，不适合放进 git |
| 凭据 | ❌ | PAT 只存在本机凭据服务，绝不进仓库 |
| 运行时 `dsh-runtimes` | ❌ | 二进制，各机器自己装 |
| 缓存 | ❌ | `storages`、`.plugin-manager/asar-out` 都能重建 |

代码仓库的提交、分支、图谱不在这里——那些交给 better-sidebar 的「Git」Tab。

## 安装

```bash
dsh plugin --profile <你的 profile> add dsh-repot
```

或从市场安装后重启 DSH。

装好后有两个入口：

- **设置 → 环境搬运**：配置平台、令牌、仓库、同步根
- **侧栏「Repot」**：日常的上传 / 比对 / 应用

没有装 better-sidebar 时只有设置页，操作区会出现在那里。

## 第一次使用

**1. 准备仓库**（私有即可），在设置页填入 `owner/repo` 和分支。三类集默认都用这个仓库；要分开（比如插件放 Gitee、文件放 GitHub），在「分集仓库」里单独指定，留空即沿用默认。

**2. 填 Personal Access Token。** 这不是 DSH 密码。GitHub 需要 `repo` 权限；Gitee 需要仓库读写权限。令牌存进 DSH 凭据服务，任何接口都不会把它读回来。

**3. 登记同步根。** 根是跨机器的锚点，比如：

| id | 路径 |
|---|---|
| `work` | `D:\work` |
| `plugins` | `C:\Users\你\.dsh\plugins` |

规则：最多 3 个，不能是盘符根（`D:\`），目录必须已存在，互不嵌套。`id` 保持不变，路径在新机器上重新指定——这就是换机器时唯一需要人工确认的东西。

**4. 在侧栏选要搬的东西**，点「上传」。

**5. 另一台机器**：装本插件，配同一个仓库和令牌，登记根，点「比对」，然后「应用」。

## 三个按钮

| 按钮 | 做什么 | 风险 |
|---|---|---|
| **上传** | 把本机选中的内容写进仓库，一次一个 commit | 只写远端 |
| **比对** | 读远端清单，和本机逐项比对 | 只读 |
| **应用** | 按比对结果写本机 | **会改本机文件**，必须先确认 |

「应用」需要显式确认；涉及文件夹时会先弹预检，把每个将要写入的绝对路径列出来。

## 路径为什么不会错

每个文件夹条目记三样东西：

```
absPath   D:/work/notes        来源机器上的绝对路径
rootId    work                你登记的根
relPath   notes               根内的相对路径
```

还原时按顺序判定：

| 级 | 条件 | 行为 |
|---|---|---|
| 1 | `absPath` 在本机存在 | 直接用 |
| 2 | `rootId` + `relPath` 在本机存在 | 重定位（换机器） |
| 3 | 都不存在 | 新建，**需要你在预检对话框里确认** |

任何一级都要再过四道拒绝：

1. 目标必须在已登记的根内 —— 挡 `..` 逃逸
2. 目标的最近存在祖先经 `realpath` 后仍须在根内 —— 挡 junction 跳出
3. 目标已存在但**没有本插件的 marker** —— 拒绝覆盖（不会吃掉你手写的目录）
4. 内容哈希与清单不符 —— 拒绝写入

剪枝只删**上一次 marker 里登记过的文件**。你自己往那个目录里放的东西不会被删。

## 插件为什么分三种

| 形态 | 仓库里存什么 | 还原动作 |
|---|---|---|
| registry | `name@version`（默认，几乎不占体积） | `installBundle('name@version')` |
| registry + 携带 | tarball | 下载后 `installBundle(tgz)` |
| `file:` 源码 | 源码目录 | 落到 `<profile>/plugins/<name>` 再装 |

大包（>20MB）默认不携带，因为 `dsh-boot-suite` 这类插件本身就带几十 MB 视频音频，塞进仓库没有意义。需要离线可用的，单个条目切到「携带」。

`package.json` 里的 `file:D:/...` 绝对路径在还原时会被改写成 `file:./plugins/<name>`——相对路径，换机器不用再改。

## 安全边界

- PAT 只在凭据服务里，不进设置文件、不进响应、不进提交信息
- 每次请求都过 `ctx.connection.requestRejection`，跨源请求直接 403
- 配置还原前先把原文件备份到 `<profile>/.repot/backup/<时间戳>/`
- 更新远端分支用 `force: false`，远端前进过就报错而不是覆盖

## 已知限制

- **会话/任务不同步**：格式与体积都不适合 git。
- **Gitee 走逐文件写入**：没有可靠的 Trees 接口，文件多时会慢，且删除文件无法在同一次提交里表达。
- **不做三方合并**：冲突一律拒绝并报告，不猜。
- **多仓库并行、submodule、Git LFS** 都不支持。
- 市场要求仓库创建满 1 天，新仓库提交会被挂起（不是拒绝）。

## 与 dsh-plugin-git-sync 的关系

dsh-repot 是它的继任者。首次启动会读取旧的 `<profile>/.git-sync/settings.json` 与 `GIT_SYNC_*` 凭据，迁移到新位置，**旧文件保留不动**，方便回退。两个插件不要同时启用。
